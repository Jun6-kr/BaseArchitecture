# 게임 프로그래밍 패턴 질답과 오답 포인트

패턴은 이름을 외우는 목록이 아니라 반복되는 문제와 트레이드오프를 공유하는 언어다. 문제 없이 패턴부터 도입하지 않는다.

## 1. 디자인 패턴 다시 보기

### Q1. 명령(Command) 패턴은 무엇을 분리하는가?

**답변**

요청을 객체로 캡슐화해 요청을 발생시키는 코드와 실행하는 코드를 분리한다. 입력 매핑, 실행 취소, 리플레이, 네트워크 명령 큐에 활용할 수 있다.

**오답 포인트**

- 모든 함수 호출을 명령 객체로 바꾸지 않는다. 큐잉·기록·취소 같은 요구가 있을 때 가치가 생긴다.

### Q2. 플라이웨이트(Flyweight) 패턴의 목적은?

**답변**

많은 객체가 공유할 수 있는 고유 상태를 한곳에 두고, 위치·체력 같은 개별 상태만 각 객체가 가진다. 타일, 나무 모델, 글리프처럼 동일 데이터가 반복될 때 메모리를 줄인다.

**오답 포인트**

- 공유 상태를 실수로 수정 가능하게 만들면 모든 인스턴스에 영향이 간다.

### Q3. 관찰자(Observer) 패턴의 장단점은?

**답변**

발행자가 구독자의 구체 타입을 몰라도 이벤트를 알릴 수 있어 결합도를 낮춘다. 반면 호출 흐름이 숨고, 구독 해제 누락·수명 문제·알림 중 목록 변경 문제가 생길 수 있다.

**오답 포인트**

- “느슨한 결합”이 의존성이 없다는 뜻은 아니다. 이벤트 계약과 수명 규칙에는 의존한다.

### Q4. 프로토타입(Prototype) 패턴은 언제 쓰는가?

**답변**

구체 타입을 직접 알지 않고 기존 객체를 복제해 새 객체를 만든다. 런타임 구성이나 데이터 기반 생성에 유용하다. C++에서는 복사 의미와 소유 자원의 깊은 복사를 명확히 설계해야 한다.

**오답 포인트**

- 원시 포인터 멤버가 있는 객체를 기본 복사해 독립 복제라고 생각하지 않는다.

### Q5. 싱글턴의 가장 큰 위험은?

**답변**

전역 접근과 단일 인스턴스를 결합해 의존성이 숨고 테스트 격리가 어려워지며 초기화·종료 순서와 멀티스레드 문제가 생긴다. 인스턴스 하나가 필요하더라도 명시적 소유와 의존성 주입이 더 나을 수 있다.

**오답 포인트**

- 생성자를 private으로 만들었다고 설계 문제가 해결되는 것은 아니다.

### Q6. 상태(State) 패턴과 전략(Strategy) 패턴은 어떻게 다른가?

**답변**

구조는 비슷하게 동작 객체에 위임한다. 상태 패턴은 객체 내부 상태 전이와 상태별 행동을 모델링하고, 전략 패턴은 같은 문제를 푸는 교체 가능한 알고리즘을 선택한다.

**오답 포인트**

- 이름보다 “누가 언제 교체하고 왜 교체하는가”로 구분한다.

## 2. 순서 패턴

### Q7. 이중 버퍼(Double Buffer)는 무엇을 해결하는가?

**답변**

한 버퍼를 읽는 동안 다른 버퍼에 다음 상태를 작성하고, 완성 시 두 버퍼를 교체한다. 렌더링 찢김이나 업데이트 중간 상태 노출을 막는다.

**오답 포인트**

- 메모리가 두 배 가까이 들고, 교체 시점과 동기화가 필요하다.

### Q8. 게임 루프의 핵심 책임은?

**답변**

입력 처리, 시뮬레이션 업데이트, 렌더링을 지속적으로 조율한다. 렌더 프레임과 시뮬레이션 시간의 관계를 고정 시간 간격, 가변 시간 간격, 누적기 방식 등으로 설계한다.

**오답 포인트**

- 프레임 수를 게임 속도로 직접 사용하면 하드웨어에 따라 동작이 달라진다.

### Q9. 고정 시간 간격 업데이트의 장단점은?

**답변**

물리와 결정론적 시뮬레이션이 안정적이고 재현하기 쉽다. 프레임이 느릴 때 여러 번 업데이트해야 하며, 따라잡지 못하면 spiral of death가 생길 수 있어 최대 업데이트 횟수 제한이 필요하다.

**오답 포인트**

- 고정 업데이트만으로 네트워크 결정론이 자동 보장되지는 않는다. 부동소수점, 실행 순서, 랜덤 시드도 통제해야 한다.

### Q10. 업데이트 메서드 패턴의 위험은?

**답변**

각 객체가 프레임마다 자신의 동작을 갱신해 전체 흐름을 단순화한다. 그러나 객체 간 업데이트 순서 의존성, 프레임 도중 생성·삭제, 매 프레임 전체 순회의 비용을 관리해야 한다.

**오답 포인트**

- 모든 객체에 무조건 `Tick`을 주지 않는다. 이벤트나 스케줄링으로 불필요한 업데이트를 줄일 수 있다.

## 3. 행동과 디커플링 패턴

### Q11. 바이트코드 패턴은 왜 필요한가?

**답변**

게임 동작을 작은 명령 집합으로 표현하고 가상 머신이 실행하게 해, 엔진 재컴파일 없이 데이터로 행동을 정의할 수 있다. 스크립트 샌드박스와 이식성을 얻는 대신 VM 구현·디버깅·성능 비용이 생긴다.

**오답 포인트**

- 네이티브 코드보다 항상 빠르거나 안전한 것은 아니다. 명령 집합과 검증 규칙에 달려 있다.

### Q12. 하위 클래스 샌드박스는 무엇인가?

**답변**

기반 클래스가 제한된 보호 API를 제공하고 파생 클래스가 그 API 조합으로 기능을 구현하게 한다. 반복되는 저수준 작업을 기반 클래스가 통제할 수 있지만 상속 결합과 기반 클래스 비대화 위험이 있다.

**오답 포인트**

- 모든 변형을 상속으로 해결하지 않는다. 조합이 더 유연한 경우가 많다.

### Q13. 타입 객체(Type Object) 패턴은 언제 쓰는가?

**답변**

클래스 상속으로 표현하던 종류 정보를 런타임 객체로 분리한다. 몬스터 종족이나 아이템 타입을 데이터로 추가할 수 있어 코드 재컴파일을 줄인다.

**오답 포인트**

- 타입 객체와 개별 인스턴스 상태의 소유권을 섞지 않는다.

### Q14. 컴포넌트 패턴의 목적은?

**답변**

거대한 게임 객체를 렌더링, 물리, 입력, AI 같은 독립 기능 객체로 나눈다. 조합으로 다양한 엔티티를 만들고 하위 시스템 경계를 명확히 한다.

**오답 포인트**

- 컴포넌트끼리 서로 직접 참조하게 만들면 결합도가 다시 높아진다. 메시지, 소유 엔티티, 시스템 인터페이스를 신중히 고른다.

### Q15. 이벤트 큐와 관찰자는 어떻게 다른가?

**답변**

관찰자는 보통 발행 순간 구독자를 동기 호출한다. 이벤트 큐는 이벤트를 저장했다가 다른 시점이나 스레드에서 소비해 시간적 결합을 낮춘다. 대신 지연, 순서, 큐 용량, 이벤트 데이터 수명을 설계해야 한다.

**오답 포인트**

- 비동기화하면 문제가 사라지는 것이 아니라 실패 처리와 디버깅이 더 어려워질 수 있다.

### Q16. 서비스 로케이터의 장단점은?

**답변**

오디오나 로깅 같은 서비스의 구현을 중앙 조회점 뒤에 숨긴다. 널 서비스로 호출부를 단순화할 수 있지만 의존성이 생성자에 드러나지 않아 전역 상태와 비슷한 문제가 생긴다.

**오답 포인트**

- 접근이 편하다는 이유만으로 모든 시스템을 등록하지 않는다. 명시적 의존성 주입과 비교한다.

## 4. 최적화 패턴

### Q17. 데이터 지역성 패턴의 핵심은?

**답변**

함께 처리하는 데이터를 메모리에서도 가깝게 배치해 캐시 미스를 줄인다. 구조체 배열을 배열들의 구조로 바꾸거나, 활성 객체를 조밀하게 모으는 방식이 있다.

**오답 포인트**

- 객체지향 추상화만 보고 메모리 접근 순서를 무시하지 않는다. 최적화 전후를 프로파일링한다.

### Q18. 더티 플래그 패턴은?

**답변**

파생 값의 원본이 바뀌었음을 표시하고 실제 필요할 때 한 번만 다시 계산한다. 월드 변환, 저장 데이터, 렌더 캐시에 유용하다.

**오답 포인트**

- 플래그 전파를 빠뜨리면 오래된 값을 사용한다. 갱신 책임과 읽기 시점을 명확히 한다.

### Q19. 객체 풀 패턴은 언제 유용한가?

**답변**

총알·파티클처럼 같은 종류의 객체를 자주 생성·파괴할 때 미리 확보한 슬롯을 재사용해 할당 비용과 단편화를 줄인다.

**오답 포인트**

- 재사용 시 모든 상태를 초기화해야 한다.
- 최대 크기를 과도하게 잡으면 메모리를 낭비하고, 너무 작으면 고갈 정책이 필요하다.

### Q20. 공간 분할 패턴은?

**답변**

객체를 위치에 따라 그리드, 쿼드 트리, 옥트리 등으로 나눠 근접 질의의 후보 수를 줄인다. 충돌의 broad phase나 주변 객체 검색에 사용한다.

**오답 포인트**

- 분할 구조 유지 비용이 있으므로 객체 이동 빈도와 분포를 고려한다.
