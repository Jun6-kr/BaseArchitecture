**학습자 답변 변화**

처음에는 “cpp 파일”이라고 답한 뒤, 전처리 과정에서 헤더 내용과 매크로가 반영된 소스라고 보완했다.

**평가: 🟡 → 🟢**

번역 단위는 하나의 소스 파일에 헤더 포함, 매크로 확장, 조건부 컴파일 등의 전처리를 적용한 결과이며 컴파일러가 독립적으로 처리하는 입력 단위다.

### Q2. `#pragma once`는 여러 번역 단위가 공유하는 헤더를 하나만 남기는가?

**학습자 답변 요약**

공유되는 하나의 헤더 객체가 생기는 것은 아니며, 각 번역 단위에 헤더 내용이 들어간다고 답했다.

**평가: 🟢**

`#pragma once`는 한 번역 단위 안에서 같은 헤더가 반복 포함되는 것을 방지한다. 프로그램 전체의 ODR 위반을 해결하지는 않는다.

### Q3. 선언만 있고 정의가 없는 함수는 항상 링크 오류인가?

**학습자 답변 요약**

함수가 호출되어야 링크 오류가 발생한다고 답했다.

**평가: 🟢**

함수가 사용되어 정의가 필요해질 때 링크 오류가 발생한다. 호출뿐 아니라 함수 주소를 취하는 경우도 정의가 필요할 수 있다.

## 질답 기록

### Q1. 선언과 정의의 차이는?

**학습자 답변 요약**

선언은 어떤 구조의 함수가 있음을 알리고, 정의는 그 함수가 내부에서 수행할 작업을 알리는 것이라고 답했다.

**평가: 🟢**

선언은 이름과 타입 등의 정보를 컴파일러에 알린다. 정의는 선언의 역할에 더해 함수 본문, 변수의 저장 공간, 완전한 클래스 본문처럼 실제 엔티티를 제공한다. 모든 정의는 선언이지만 모든 선언이 정의는 아니다.

### Q2. 다음 코드는 선언인가, 정의인가?

```cpp
void Print();                 // 선언
void Print() {}               // 정의
extern int score;             // 선언
int score;                    // 정의
class Player;                 // 선언
class Player { int hp; };     // 정의
```

**학습자 답변 변화**

처음에는 오타로 2번과 5번이 정의라고 답했으나, 2번과 6번을 의도했다고 정정했다. `int score;`가 정의인 이유를 질문했다.

**평가: 🟡 → 🟢**

`int score;`는 변수의 저장 공간을 제공하므로 정의다. 일반적인 `extern int score;`는 다른 곳에 정의가 있음을 알리는 선언이다. 단, `extern int score = 0;`처럼 초기화하면 정의가 된다.

### Q3. 전방 선언만으로 가능한 작업은?

**학습자 답변 요약**

`Player*`와 `Player&`는 가능하지만, `Player` 객체를 직접 만들거나 `sizeof(Player)`를 사용하는 것은 완전한 클래스 정보가 필요하다고 답했다.

**평가: 🟢**

포인터와 참조의 크기는 대상 타입의 전체 정의 없이도 알 수 있다. 객체의 크기나 배치를 알아야 하는 작업은 완전한 타입이 필요하다.

### Q4. `Enemy`가 `Player*`를 보관하고 `.cpp`에서 멤버 함수를 호출한다면 헤더를 어디서 포함하는가?

**학습자 답변 요약**

`Enemy.h`에는 `class Player;`만 두고 `Enemy.cpp`에서 `Player.h`를 포함하는 것이 좋다고 답했다. 불필요한 전처리 내용과 순환 포함 가능성도 이유로 들었다.

**평가: 🟢**

정확하다. 핵심 효과는 헤더 간 결합과 재컴파일 범위를 줄이는 것이다. `Enemy.cpp`에서 `Player`의 멤버를 호출하는 시점에는 완전한 타입이 필요하다.

### Q5. ODR은 “하나의 선언에 하나의 정의”라는 뜻인가?

**학습자 답변 요약**

선언과 정의가 하나씩 있어야 하며 오버로딩에도 관련된다고 추측했다.

**평가: 🟡**

호환되는 선언은 여러 번 반복될 수 있다. 일반적으로 외부 연결을 가진 비인라인 함수나 변수의 정의는 프로그램 전체에 하나만 있어야 한다. 클래스, 템플릿, `inline` 함수와 변수처럼 조건을 만족하는 동일한 정의가 여러 번역 단위에 나타날 수 있는 예외도 있다. 오버로드들은 서로 다른 함수이므로 각각에 ODR이 적용된다.

### Q6. 반복 선언과 중복 정의는 각각 허용되는가?

**학습자 답변 요약**

호환되는 함수 선언의 반복은 괜찮고, 일반 함수 정의가 두 `.cpp`에 있으면 문제가 되며, 헤더의 `inline` 함수 정의는 괜찮다고 답했다.

**평가: 🟢**

호환되는 선언은 반복할 수 있지만 반환형이나 타입 정보가 충돌하면 컴파일 오류가 발생한다. 매개변수 목록이 다르면 중복 선언이 아니라 오버로드일 수 있다.

### Q7. `inline` 키워드의 역할은?

**학습자 답변 변화**

처음에는 알지 못한다고 답했다. 이후 최적화 여부는 컴파일러가 결정하며, 호출부를 함수 본문으로 치환하도록 요청하는 의미로 알고 있다고 설명했다. 최종적으로 헤더에 정의된 동일한 함수가 여러 번역 단위에 생기는 것을 허용하는 언어적 역할을 이해했다.

**평가: 🟡 → 🟢**

현대 C++에서 `inline`의 중요한 언어적 역할은 동일한 정의가 여러 번역 단위에 나타나는 것을 허용하는 것이다. 실제 최적화 인라이닝은 함수 호출을 본문으로 대체해 호출 비용을 줄이고 상수 전파 등의 추가 최적화를 가능하게 하지만, `inline` 키워드와 독립적으로 컴파일러가 판단한다.

### Q8. 헤더에 정의한 일반 함수의 중복 정의 문제를 해결하는 두 방법은?

**학습자 답변**

헤더에는 선언만 남기고 정의를 `.cpp`에 두거나, `inline`을 추가해 여러 번역 단위의 동일한 정의를 허용한다고 답했다.

**평가: 🟢**

일반적인 구현 분리에는 전자를 사용하고, 짧은 헤더 정의나 템플릿처럼 헤더에 정의가 필요할 때는 후자를 사용한다. `#pragma once`만으로는 서로 다른 번역 단위 사이의 중복 정의를 막지 못한다.

### Q9. 헤더에 `int maxPlayerCount = 4;`를 작성하면?

**학습자 답변 변화**

처음에는 클래스 객체마다 별도 메모리가 생기는 상황으로 이해하고 클래스 `static`을 떠올렸다. 예제가 클래스 밖의 전역 변수라는 점을 확인한 뒤 전역 변수의 연결 개념을 학습했다.

**평가: 🟡**

헤더의 `int maxPlayerCount = 4;`는 외부 연결을 가진 전역 변수의 정의이므로 여러 번역 단위에서 중복 정의 문제가 생긴다. 하나의 변수를 공유하려면 헤더에 `extern int maxPlayerCount;`, 한 `.cpp`에 `int maxPlayerCount = 4;`를 작성한다. C++17부터는 헤더에 `inline int maxPlayerCount = 4;`를 정의할 수도 있다.

### Q10. 헤더의 전역 `static` 변수를 여러 `.cpp`가 포함하면?

**학습자 답변 요약**

`A.cpp`의 변수와 `B.cpp`의 변수를 별개로 보아야 하므로, A에서 증가시켜도 B에서는 초기값 0이 출력된다고 답했다.

**평가: 🟢**

네임스페이스 범위의 `static`은 내부 연결을 부여한다. 링크 오류는 없지만 번역 단위마다 서로 다른 변수가 생긴다.

### Q11. 클래스의 `static` 데이터 멤버는 어디서 정의하는가?

**학습자 답변 변화**

클래스 또는 `main` 외부에서 초기화해야 하는지 추측했다. 설명 후 클래스 안의 선언과 `.cpp`의 네임스페이스 범위 정의를 구분했고, C++17의 `inline static` 방식도 이해했다.

**평가: 🟡 → 🟢**

```cpp
// GameConfig.h
class GameConfig
{
public:
    static int maxPlayerCount;
};

// GameConfig.cpp
int GameConfig::maxPlayerCount = 4;
```

C++17부터는 클래스 안에서 다음과 같이 선언과 정의를 함께 할 수 있다.

```cpp
inline static int maxPlayerCount = 4;
```

### Q12. 전역 `static`과 클래스 `inline static`의 변수 개수는?

**학습자 답변 변화**

세 번역 단위가 헤더를 포함할 때 처음에는 둘 다 하나라고 추측했다. 교정 후 전역 `static`은 번역 단위마다 하나, 클래스의 `inline static`은 프로그램 전체에 하나임을 구분했다.

**평가: 🔴 → 🟢**

- 헤더의 전역 `static int count`: 내부 연결이므로 세 번역 단위에 세 개
- 클래스의 `inline static int count`: 모든 객체와 번역 단위가 공유하는 하나

### Q14. 클래스 `static` 멤버 선언만 있고 정의가 없다면?

**학습자 답변**

## 오답 및 보완 항목

### 1. ODR을 “선언 하나, 정의 하나”로 기억한 점

- 오답 경향: 선언도 하나만 있어야 한다고 생각함.
- 교정: 호환되는 선언은 여러 번 가능하다. 제한의 핵심은 정의이며, `inline`, 클래스, 템플릿 등의 예외 조건이 있다.

### 2. `inline` 키워드와 최적화 인라이닝

- 오답 경향: `inline`을 함수 본문 치환 요청으로만 이해함.
- 교정: 실제 인라이닝 여부는 컴파일러가 판단한다. 키워드의 핵심 언어적 역할은 여러 번역 단위의 동일한 정의를 허용하는 것이다.

### 3. 전역 변수와 클래스 멤버 변수의 구분

- 오답 경향: 클래스가 없는 전역 변수 예제를 객체별 저장 공간 문제로 해석함.
- 교정: 먼저 선언 위치가 네임스페이스 범위인지 클래스 범위인지 확인한다.

### 4. `static`의 문맥별 의미

- 오답: 헤더의 전역 `static` 변수도 프로그램 전체에 하나라고 추측함.
- 교정: 전역 `static`은 내부 연결로 인해 번역 단위마다 하나씩 생긴다. 클래스의 `static` 데이터 멤버는 객체들이 하나를 공유한다.

## 최종 30초 답변

> 선언은 이름과 타입을 알리고 정의는 함수 본문, 변수 저장 공간, 완전한 클래스처럼 실제 엔티티를 제공합니다. 호환되는 선언은 반복할 수 있지만 일반적인 외부 연결 함수와 변수의 정의는 프로그램 전체에 하나여야 합니다. 헤더에 정의가 필요하면 `inline`을 사용해 여러 번역 단위의 동일한 정의를 허용할 수 있습니다. 하나의 전역 변수를 공유하려면 헤더에 `extern` 선언과 `.cpp`에 정의를 두고, 번역 단위마다 별도 변수가 필요하면 전역 `static`, 객체들이 공유하는 클래스 멤버가 필요하면 클래스 `static`을 사용합니다.
