## 이전 학습 복습

### Q1. 전역 `static`과 클래스의 `inline static`은 각각 몇 개 생기는가?

**학습자 답변 요약**

세 번역 단위가 헤더를 포함하면 전역 `static` 변수는 세 개, 클래스의 `inline static` 멤버는 하나라고 답했다.

**평가: 🟢**

전역 `static`은 내부 연결로 인해 번역 단위마다 별도 변수가 생긴다. 클래스의 `static`은 객체들이 하나의 멤버를 공유한다는 뜻이고, `inline`은 헤더의 동일한 정의가 여러 번역 단위에 나타나는 것을 허용한다.

### Q2. `extern` 선언만 있고 정의 파일이 빌드에서 빠지면?

**학습자 답변 요약**

선언을 통해 이름과 타입을 알 수 있어 컴파일은 통과하지만 실제 정의를 찾지 못해 링크 오류가 발생한다고 답했다.

**평가: 🟢**

정확하다. 변숫값을 읽는 사용은 정의를 요구하므로 링커가 해당 심볼을 해결해야 한다.

### Q3. 전방 선언된 타입의 멤버 함수를 호출하려면?

**학습자 답변 요약**

포인터 선언은 전방 선언으로 충분하지만 멤버 함수 호출에는 클래스 정의가 필요하므로 `Player`가 정의된 헤더를 포함해야 한다고 답했다.

**평가: 🟢**

`Enemy.cpp`에서는 자기 헤더인 `Enemy.h`를 먼저 포함하고, 이어서 완전한 타입을 제공하는 `Player.h`를 포함하는 것이 좋다.

## 질답 기록

### Q1. 지역 객체의 생성자와 소멸자 호출 순서는?

```cpp
Trace a("A");
{
    Trace b("B");
    Trace c("C");
}
Trace d("D");
```

**학습자 답변**

`A → B → C → ~B → ~C → D → ~A → ~D`라고 예상했다.

**평가: 🔴**

정확한 순서는 `A → B → C → ~C → ~B → D → ~D → ~A`다. 자동 저장 기간의 지역 객체는 스코프를 벗어날 때 생성의 역순으로 소멸한다.

### Q2. 조기 `return`이 발생하면 지역 객체는 어떻게 되는가?

**학습자 답변 요약**

이미 생성된 `game`의 소멸자는 호출되며, 실행 흐름이 도달하지 않은 `player`는 생성·소멸되지 않는다고 답했다. 자원 사용을 조건에 따라 피할 수 있다는 장점도 언급했다.

**평가: 🟢 / 장점 설명은 🟡**

핵심 장점은 정상 종료, 조기 반환, 예외 등 어떤 경로로 스코프를 벗어나더라도 이미 획득한 자원을 자동으로 정리할 수 있다는 것이다.

### Q3. 직접 `new[]/delete[]`를 관리하는 코드에서 조기 반환하면?

**학습자 답변 요약**

힙 메모리 누수가 발생한다고 답했고, 스마트 포인터를 사용하면 객체 소멸 시 자동으로 자원을 해제할 수 있다고 설명했다.

**평가: 🟢**

배열 소유권이 필요하면 `std::make_unique<int[]>(100)`을 사용할 수 있다. 단순한 동적 배열 컨테이너가 목적이라면 `std::vector<int>`가 더 자연스럽다.

### Q4. 클래스와 멤버 객체의 생성·소멸 순서는?

**학습자 답변**

`Player` 생성자 본문이 실행된 뒤 `weapon`, `armor`가 생성되고, 멤버들이 소멸한 뒤 `Player` 소멸자 본문이 실행된다고 예상했다.

**평가: 🔴**

정확한 순서는 다음과 같다.

```text
Create Weapon
Create Armor
Player constructor
Player destructor
Destroy Armor
Destroy Weapon
```

객체의 생성자 본문은 모든 멤버가 준비된 뒤 실행된다. 소멸자 본문은 먼저 실행되고, 그 후 멤버들이 선언의 역순으로 소멸한다.

### Q5. 멤버 생성 순서는 무엇이 결정하는가?

**학습자 답변 요약**

초기화 목록의 표기 순서가 아니라 멤버 선언 순서가 우선한다고 답했다. 먼저 선언된 멤버를 뒤 멤버의 초기화에 사용할 수 있지만 그 반대는 안전하지 않다고 설명했다.

**평가: 🟢**

정확하다. 혼동과 초기화 전 값 사용을 피하도록 초기화 목록도 선언 순서에 맞춰 작성하는 것이 좋다.

### Q6. 기반 클래스, 멤버, 파생 클래스의 생성·소멸 순서는?

**학습자 답변**

기반 클래스와 파생 클래스 생성자 본문이 실행된 뒤 멤버가 생성되고, 파생·기반 클래스 소멸자 본문 이후 멤버가 소멸한다고 예상했다.

**평가: 🔴**

정확한 순서는 다음과 같다.

```text
Character constructor
Create Weapon
Player constructor
Player destructor
Destroy Weapon
Character destructor
```

생성은 기반 클래스 → 멤버 → 파생 클래스 생성자 본문 순서이며, 소멸은 정확히 그 역방향이다.

### Q7. 예외가 발생하면 이미 생성된 지역 객체는 어떻게 되는가?

**학습자 답변 요약**

`game`, `player`만 생성되고 예외 발생 후 `player`, `game` 순서로 소멸하며, 실행 흐름이 도달하지 않은 `enemy`는 생성되지 않는다고 답했다.

**평가: 🟢**

예외 처리기를 찾으며 호출 스택을 되돌리는 스택 풀기 과정에서 완전히 생성된 자동 객체가 역순으로 소멸한다.

### Q8. 지역 객체의 주소를 반환하면?

**학습자 답변 요약**

함수 종료와 함께 지역 객체의 수명이 끝나므로 반환된 포인터가 이미 소멸된 공간을 가리키는 댕글링 포인터가 된다고 답했다. 우연히 기존 값이 출력돼도 안전하지 않다고 판단했다.

**평가: 🟢**

포인터에 주소값이 남아 있는 것과 그 주소에 살아 있는 객체가 존재하는 것은 다르다. 수명이 끝난 객체를 역참조하면 정의되지 않은 동작이다.

### Q9. 값 반환, 원시 포인터 반환, `unique_ptr` 반환 중 무엇을 선택하는가?

**학습자 답변 요약**

단순한 점수 하나라면 값 반환이 가장 적절하며, `new`로 만든 원시 포인터는 명시적으로 해제하지 않으면 누수된다고 답했다. `unique_ptr`은 반환받은 포인터가 소유권을 갖고 소멸할 때 자원을 해제한다고 설명했다.

**평가: 🟢**

값으로 충분하면 값을 반환하고, 동적 수명과 소유권 전달이 실제로 필요할 때 스마트 포인터를 사용한다.

### Q10. 생성자 본문에서 예외가 발생하면 완성되지 않은 객체의 소멸자가 호출되는가?

**학습자 답변 요약**

완성된 멤버들을 정리하려면 멤버 소멸자들과 함께 바깥 객체의 소멸자도 호출될 것이라고 예상했다.

**평가: 🔴**

생성자가 정상 완료되지 않았으므로 완성된 바깥 객체가 존재하지 않으며 그 객체의 소멸자는 호출되지 않는다. 대신 생성이 완료된 멤버들은 언어가 자동으로 역순 소멸시킨다.

### Q11. 두 번째 멤버 생성 중 예외가 발생하면?

**학습자 답변**

앞서 생성이 완료된 첫 번째 멤버의 소멸자만 호출된다고 답했다.

**평가: 🟢**

정확하다. 생성에 실패한 멤버와 완성되지 않은 바깥 객체에는 소멸자를 호출하지 않는다.

### Q12. RAII를 면접 답변으로 설명하면?

**학습자 답변 요약**

자원의 생성·소멸을 객체의 생성·소멸에 맞춰 직접 해제를 누락하는 실수를 줄이는 개념이라고 설명했다. 객체 소멸 시 자원이 자동 해제되며 `vector`와 스마트 포인터를 예로 들었다.

**평가: 🟡**

핵심 개념은 맞다. 다만 “생성 완료 전 `return`”이 아니라 함수의 조기 반환이나 예외로 스코프를 벗어나는 상황이라고 표현해야 한다. `weak_ptr`는 자원을 소유하지 않으므로 대표적인 소유 RAII 타입으로는 `vector`, `unique_ptr`, `shared_ptr`, `lock_guard`가 적절하다.

## 오늘 잘한 점

- 조기 반환과 예외 상황에서도 이미 생성된 객체가 정리된다는 점을 이해했다.
- 동적 배열 누수의 원인과 스마트 포인터·`vector`를 이용한 해결 방향을 정확히 제시했다.
- 멤버의 실제 초기화 순서가 선언 순서로 결정된다는 사실을 정확히 기억했다.
- 댕글링 포인터에서 주소값의 존재와 객체 수명의 유효성을 구분했다.
- 값 반환과 소유권 반환을 요구사항에 따라 선택했다.
- 생성에 실패한 멤버는 소멸하지 않고, 앞서 완성된 멤버만 정리된다는 점을 교정 후 정확히 답했다.

## 오답 및 보완 항목

### 1. 같은 스코프의 소멸 순서

- 오답: 먼저 생성된 객체부터 소멸한다고 예상함.
- 교정: 자동 객체는 같은 스코프에서 생성의 역순으로 소멸한다.

### 2. 멤버와 바깥 객체의 순서

- 오답: 클래스 생성자 본문 이후 멤버가 생성되고, 멤버 소멸 이후 클래스 소멸자 본문이 실행된다고 예상함.
- 교정: 멤버가 먼저 생성된 뒤 생성자 본문이 실행된다. 소멸자 본문이 먼저 실행된 뒤 멤버가 역순 소멸한다.

### 3. 기반 클래스·멤버·파생 클래스의 순서

- 교정: 생성은 기반 클래스 → 멤버 → 파생 클래스 본문이며, 소멸은 파생 클래스 본문 → 멤버 → 기반 클래스다.

### 4. 생성 실패와 바깥 객체의 소멸자

- 오답: 생성자 본문에서 예외가 발생해도 바깥 객체의 소멸자가 호출된다고 예상함.
- 교정: 완전히 생성되지 않은 객체의 소멸자는 호출되지 않는다. 이미 완성된 기반 객체와 멤버만 역순으로 정리된다.

### 5. RAII 설명의 표현

- 보완: 생성 중 `return`보다 함수의 조기 반환과 예외에 의한 스코프 이탈로 설명한다.
- 보완: `weak_ptr`는 비소유 관찰자이며 자원 수명을 직접 관리하지 않는다.

## 최종 30초 답변

> RAII는 자원의 획득과 해제를 객체 수명에 결합하는 기법입니다. 생성 과정에서 자원을 획득하고 소멸자에서 해제하므로 함수가 정상 종료되거나 조기 반환·예외로 스코프를 벗어나도 자동으로 정리됩니다. 따라서 모든 실행 경로에 `delete`, `close`, `unlock`을 직접 작성할 때 생기는 누락을 방지할 수 있습니다. 대표적으로 `std::vector`, `std::unique_ptr`, `std::shared_ptr`, `std::lock_guard`가 있습니다.
